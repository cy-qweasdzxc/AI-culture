# 多角色同场对话

一轮用户输入交给导演 Agent 排定剧情节拍与发言顺序，再由旁白 Agent 衔接现场、角色 Agent 各自回答。页面可以把当前点位的角色与本次旅程中实际交谈过的角色放进同一场景；导演根据玩家点名、问题和当前进度重新安排下一轮。

## 职责与权限

- **导演**读取当前旅程状态、合法角色、最近对话及下一步建议，产出本轮节拍、目标、节奏和发言顺序。它只编排本轮表达，不能直接完成任务、发放奖励、解锁未来点位或选择结局。
- **旁白**根据导演节奏从安全舞台句候选中选择本轮的衔接与气氛文字。它不承担文化史实回答，不得代替用户移动、作答或作出结局选择。
- **角色**保留原有的人物口吻、检索与逐句证据核验。当前点位角色只能使用当前允许的已审核资料；远程同行角色只能使用本旅程此前已经向玩家披露、目前仍合格的证据。角色不能因为加入群聊而获得未来知识。
- **服务端状态机**仍是进度与奖励的唯一来源。导演的下一步是建议，用户仍须使用既有任务、点位、结局接口执行实际操作。

一轮最多三个 NPC。玩家身份角色、未知 NPC、其他故事 NPC 与尚未遇见的未来 NPC 不能加入。锚点 NPC 是当前打开的对话入口；同场消息统一归入该入口，避免把同行发言复制到多个聊天记录中。

导演能读取本旅程近期公开对话，按玩家点名、角色专长、追问、打断或推进意图安排这一轮。各角色的检索准备可并行执行；正式发言按导演顺序进行，后发角色可以看到同轮先发角色已经过核验的内容。共享对话只用于理解话题与衔接，不能代替该角色自己的文化证据。

点名顺序会被保留，例如「周伯先说，再请阿蘅补充」；「阿蘅先别说，让周伯发言」会排除被要求暂时沉默的角色。明确的「继续剧情」「接下来该做什么」等续场操作使用作者编写的当前进度引导，标记 `reason=NARRATIVE_GUIDANCE`、`dataScope=authored_story`，不冒充文化证据回答，也不自动执行下一步。

## HTTP 与 SSE 契约

```http
POST /api/chat/scene/stream
Content-Type: application/json
Accept: text/event-stream
```

```json
{
  "journey_id": "当前会话的旅程 ID",
  "state_version": 12,
  "request_id": "每轮唯一且重试时保持不变的 ID",
  "npc_id": "a-heng",
  "message": "周伯先说说星桥，阿蘅再讲讲雨亭。",
  "participant_ids": ["a-heng", "zhou-bo"]
}
```

`participant_ids` 可省略；它用于在服务端允许的角色中选择本轮同行。客户端传入的角色名单不能扩大权限。`request_id` 用于重复提交与断流后恢复，不能把同一 ID 用于不同输入或不同参与者。

事件数据都是 JSON，每个事件以空行结尾。客户端按 `event:` 读取事件类型，不按网络数据块划分消息。

每个事件携带与本轮请求及事件次序对应的 `id:`，同一请求回执重放时保持稳定。`turnId` 等于请求的 `request_id`。

| 事件 | 含义 |
| --- | --- |
| `status` | 本轮处理进展，供界面展示等待状态。 |
| `director` | 本轮经校验的导演决定。 |
| `message` | 一条本轮旁白或角色消息，提交前只供临时预览。 |
| `done` | 本轮已保存，附带权威快照、导演决定与本轮完整消息。 |
| `error` | 本轮失败；不得把临时编排或未保存文字视为已完成的对话。 |

导演数据使用 camelCase：

```json
{
  "turnId": "本轮 ID",
  "beat": "本轮剧情节拍",
  "objective": "本轮目标",
  "reason": "调度原因",
  "speakerOrder": ["zhou-bo", "a-heng"],
  "pace": "explore",
  "nextAction": {"type": "task", "targetId": "task-jiaou", "label": "查看当前任务"},
  "mode": "rules"
}
```

`pace` 为 `explore | focus | transition`，`nextAction.type` 为 `chat | task | map | finale`，`targetId` 可为空。`mode` 为 `model | rules`；提供方信息可通过可选的 `provider` 字段附带。下一步只能指向当前旅程已经允许的操作，不能照单接受模型填写的目的地。

消息沿用 `ChatMessage`，新增或扩展字段：

| 字段 | 用途 |
| --- | --- |
| `from` | `user | npc | narrator | system`；`system` 用于提交成功后的线索到账提示。 |
| `npcId`、`speakerName` | 实际发言角色与显示名称，旁白有自己的显示名称。 |
| `agentRole`、`turnId` | 区分角色职责并把同轮内容分组。 |
| `feedbackNpcId`、`feedbackMessageId` | 将问题反馈精确关联到该条角色发言。 |
| `evidenceIds`、`evidence` | 保留角色的实际审核证据与引用。 |
| `provider`、`mock`、`reason` | 暴露降级与拒答信息，界面不可将拒答伪装成成功的文化回答。 |

`done` 的结构为 `{snapshot, director, messages, replayed?}`，其中 `messages` 是本轮生成的旁白、角色消息及可能出现的系统确认提示；用户消息随整轮一同保存到快照。`snapshot.sceneDirections[anchorNpcId]` 保存该入口最新导演决定；`snapshot.messages[anchorNpcId]` 保存按场次与发言顺序排列的用户、旁白、角色及系统消息。刷新、恢复会话后直接使用这份快照。

旧接口 `POST /api/chat/message` 继续可用，保留原有单角色响应与已编写的线索发放规则。

## 持久化、重试与并发

模型调用在写事务之外执行，生成期间不持有数据库写锁。所有角色结果完成后，服务端重新核验旅程版本、可参与角色与证据审核状态，再使用一次版本比较更新，把整轮对话和幂等回执一并提交。任一状态或证据失效，整轮不能落下部分对话。

一轮的可见消息与导演结果持久化在场景记录中；逐角色记录用于证据上下文与精确反馈，快照会跳过其重复展示。完成整轮只增加一次 `stateVersion`。界面可以在提交前展示 `message` 的临时内容，但只有 `done` 确认保存；收到 `error` 后应恢复权威快照，不能把先前预览保留为已保存历史。

同一 `request_id` 与相同请求体重试时读取已经保存的本轮结果，不重复调用模型、写入消息或发放奖励；同时附带最新旅程快照，避免旧重试使页面进度倒退。同一 ID 携带不同内容返回幂等冲突。新请求携带旧 `state_version` 返回状态冲突。

网络连接结束并不代表保存失败。如果没有收到 `done`，客户端应先恢复权威快照或使用原 `request_id` 和原请求体重试。不得为同一轮自动换用新 ID，也不得自行假定旅程版本已经递增。SSE 提供阶段状态和完整消息事件，不提供模型逐 token 直播。

停止接收或断开连接发生在提交边界之前时，不保存部分消息、回执或奖励；提交成功之后，即使 `done` 在网络上丢失，刷新或使用原请求重试仍可恢复整轮。已经发出的提供方 HTTP 调用不保证随浏览器停止而中止。停止接收也不等于撤销已经保存的内容。

前端采用 210 秒的整轮总超时。部署配置 `deploy/nginx/nginx.conf` 为此 SSE 路径设置专用代理规则并禁用响应缓冲，以便逐阶段送达状态与整段发言。这不改变提供方当前返回完整 JSON、角色完成一段后才推送的语义。

## 校验与降级

输入安全检查覆盖整轮。命中提示注入的输入不会进入导演、旁白、角色生成或嵌入服务；返回受控拒答，也不会改变任务、奖励与路线。

导演输出必须通过结构与权限校验，包括合法且不重复的发言者、可用的下一步和受限动作。模型超时、格式错误、指定非法角色或提出越权动作时改用规则导演。旁白不可用时使用受控衔接文字。个别角色提供方失败时保留其他角色，并对失败角色返回明确的受控拒答。

导演模型可选择合法的顺序和节奏；界面展示的节拍、目标与调度理由使用作者编排语言，避免把模型自由文本当成事实通道。公共历史在进入本轮上下文前重新检查证据资格，撤审内容不作为后续角色的事实来源。

角色输出继续使用审核证据与原文片段核验。资料撤审、正文更新或适用范围变化发生在模型等待期间时，提交前的复查会阻止陈旧内容保存。远程角色不会因为用户点名或模型要求而读取本旅程未披露的其他地点资料。

多角色接口不会把用户的聊天文字当成任务答案，也不会自动通过任务或触发结局。当前点位的既有谜题线索规则继续有效，例如玩家向周伯询问「平江图」可获得已编写的剧情线索；这些条件由服务端明确执行，与导演、旁白或角色模型提出的动作无关。同一线索只发一次。

线索发放通知只在提交确认成功后写入最终消息和快照。提交前收到的角色预览不会先宣称已经获得道具。

## 验证范围

`backend/tests/test_scene_director.py` 与 `backend/tests/test_scene_stream.py` 使用 mock 提供方、Alembic 临时 SQLite 数据库和合成审核资料验证 SSE、编排、权限、证据、并发、幂等、刷新和反馈边界；不读取开发者真实 `.env`，不调用付费服务。

这些测试验证接口行为与服务端防线。真实模型的响应延迟、并发容量、自由文本的戏剧质量、长会话连贯性，以及不同提供方的 JSON 遵循情况，仍需在配置真实提供方后另行验证。当前旁白与角色的协作是按轮编排，并不等同于无限自主运行的剧情模拟。

本机没有 Docker，本次未运行容器化 Nginx 代理，也未验证真实公网连接、代理链路或真人模型提供方；代理配置与前端超时的修改不能代替部署环境下的流式传输验收。
